# Output templates

Rupantar renders `presentation` to `.pptx` and `advisory`/`executive_summary` to `.docx`
through a **document template** — a real `.potx`/`.dotx` file loaded with python-pptx /
python-docx, not a code path with hardcoded fonts. Which template is used is a generation
parameter (`GenerationParams.template`, default `"ntro-formal"`) and can also be changed
after the fact, per artefact, without re-running the model (`POST
/transforms/{id}/jobs/{id}/render?template=<id>`).

Three templates ship today — **ntro-formal**, **executive**, **technical** — declared in
`configs/templates/templates.yaml` and backed by `configs/templates/<id>.potx` /
`configs/templates/<id>.dotx` / `configs/templates/<id>.png`. **All nine files currently on
disk are placeholders**, generated by `scripts/generate_placeholder_templates.py`: they are
structurally correct (every layout and style below exists in them) but carry no real visual
design. Replace the `.potx`/`.dotx`/`.png` files in place — the manifest and the renderers
do not need to change, as long as the replacement keeps the layouts and styles below.

## What a `.potx` must contain

`render/pptx_render.py` looks up each `Slide.layout` enum value (from the frozen `Presentation`
artefact schema — see `docs/SCHEMAS.md`) as a **layout index**, never a guessed position. The
index for each key is declared in `templates.yaml`'s `pptx.layouts` map; the template file
itself just needs that many layouts to exist, in any order, doing whatever visual design you
want with each one.

| `templates.yaml` key | Used for | What the layout needs |
|---|---|---|
| `title_slide` | The deck's opening slide (title + subtitle) | A title placeholder; one more placeholder for the subtitle is used if present |
| `title` | A `Slide.layout == "title"` content slide (a section-header-style slide) | A title placeholder |
| `bullets` | A `Slide.layout == "bullets"` content slide | A title placeholder + one body/content placeholder |
| `two_column` | A `Slide.layout == "two_column"` content slide | A title placeholder + a body placeholder (only the first body placeholder is filled today — see Known limitation below) |
| `quote` | A `Slide.layout == "quote"` content slide | A title placeholder + one body placeholder |
| `closing` | A `Slide.layout == "closing"` content slide | A title placeholder; a body placeholder if you want closing bullets shown |

Every content slide also gets a speaker-notes text frame filled automatically (python-pptx
always provides one; no template requirement there).

**It is fine for several keys to point at the same layout index** — the three shipped
placeholders do exactly this (`quote` reuses the same layout as `bullets`, `closing` reuses
`title`), because PowerPoint's own default template only ships ~9 general-purpose layouts and
that is enough. A real design only needs as many *distinct* layouts as it wants to look
different from each other; it must have at least one layout at whichever index the highest
key you use points to.

**Fallback behaviour:** a `templates.yaml` entry with no `pptx:` key, a `pptx.file` that does
not exist or will not open, or a `layouts` map missing a key or pointing at an index the
`.potx` does not actually have, degrades to python-pptx's own built-in default deck (or, for
a bad index only, the nearest in-range index) and records a warning in
`Manifest.render_warnings` on the rendered file's provenance manifest. It never raises.

## What a `.dotx` must contain

`render/docx_render.py` applies **named paragraph styles**, never inline font settings, for
six abstract keys declared in `templates.yaml`'s `docx.styles` map. The style *names* are
whatever your template calls them — `templates.yaml` maps our abstract key to your template's
real name, so two templates can use completely different style names for "heading1" as long
as each manifest entry says so correctly.

| `templates.yaml` key | Used for | A safe starting point |
|---|---|---|
| `title` | The artefact's title, as the document's opening heading | Word's built-in "Title" style |
| `heading1` | Section headings (Summary, Background, Key points, Takeaway, …) | Word's built-in "Heading 1" style |
| `heading2` | Sub-headings (advisory `technical_details[].heading`) | Word's built-in "Heading 2" style |
| `bullet` | Every bulleted list (key points, indicators, recommended actions, …) | Word's built-in "List Bullet" style |
| `severity_banner` | The classification/confidence banner, the document's very first paragraph | A new paragraph style: bold, a strong accent colour, ideally shaded/bordered so it reads as a banner, not body text |
| `classification_footer` | The page footer's provenance line | A new paragraph style: small, muted, distinct from body text |

**Fallback behaviour:** a `templates.yaml` entry with no `docx:` key, a `docx.file` that does
not exist or will not open, or a `styles` entry naming a style the `.dotx` does not actually
define, degrades per key: `title`/`heading1`/`heading2`/`bullet` fall back to Word's built-in
style of the same purpose (so headings and bullets always render correctly even with zero
template configuration); `severity_banner`/`classification_footer` have no Word built-in
equivalent, so they fall back to the original plain formatting (bold text for the banner,
plain text for the footer). Every fallback records a warning in `Manifest.render_warnings`. It
never raises.

## Adding a fourth template

1. Design the `.potx`/`.dotx` (or start from a copy of the placeholders and restyle them —
   `configs/templates/generate_placeholder_templates.py`'s output already has every required
   layout/style, just undesigned).
2. Drop the files at `configs/templates/<id>.potx`, `<id>.dotx`, and a `<id>.png` thumbnail
   (any reasonable size; it is served as-is via `GET /templates/{id}/thumbnail`).
3. Add an entry to `configs/templates/templates.yaml` with the layout indices and style names
   your files actually use — copy an existing entry as a starting point if the layout/style
   *order* matches; only the numbers/names need to change.
4. No code change, no schema change, no restart needed beyond what already reloads
   `templates.yaml` (the manifest is cached per `configs_dir` in-process — restart the API
   process to pick up a new or edited manifest during development).

## Known limitation

`two_column`'s second column is not filled today — `_body_placeholder()` in
`render/pptx_render.py` fills only the first non-title placeholder it finds on the slide. The
`Presentation` artefact schema's `Slide.bullets` is a single flat list, not split into two
columns, so there is currently nothing to put in a second placeholder even if one were filled.
Splitting `bullets` across both column placeholders (e.g. by count) is a reasonable follow-up
if `two_column` decks are actually used, but it is out of scope for this change.
